# Template snapshots on CKS

Written 2026-08-29. Companion to [tag-templates-design.md](tag-templates-design.md),
which added `snapshot bind` and made a tag select a rootfs, and to
[security-hardening.md](security-hardening.md), which is why none of it works on
the cluster.

## The problem, stated exactly

`snapshot create` is refused on CKS. `internal/vmm/firecracker/fc.go` returns
early from `Driver.Snapshot` when `DisableHostRootfsMounts` is set, and
`deploy/kubernetes/entrypoint.sh` sets it unconditionally there. Everything
built on capture inherits the refusal: `fork`, `snapshot bind`, the REST route,
the user console's button, and `sparkbox snapshot <tag>` from inside a VM. Tag
templates are present and correct on the cluster and have nothing to point at.

The flag is not a knob somebody turned the wrong way. The VM controller
container runs as uid 65532 with `capabilities: drop ALL` and cannot call
`mount(2)` at all; the remaining trusted loop mounts were deliberately moved
into the `prepare-vm-assets` init container, which exits before the node accepts
guest traffic. Mounting a guest-authored ext4 in the long-lived management
process would put the host kernel's ext4 driver — shared with every other tenant
on a CoreWeave node — into the trusted computing base, next to Firecracker and
KVM. That was the right call and this design does not revisit it.

## What actually needs the mount

`Driver.Snapshot` has four steps. Three of them do not mount anything:

| step | mounts? |
| --- | --- |
| `cp --reflink=always` (stage a copy-on-write clone) | no |
| `sanitizeTemplate` (six file deletions) | **yes** |
| `compact` — `e2fsck -fy` then `zerofree` | no |
| `os.Rename` into the image dir | no |

`e2fsck` and `zerofree` operate on the image file directly, which is why the
checkpoint path already runs them on this cluster today. **The entire refusal
rests on one function that deletes six paths.**

And that function is not a security boundary. It removes `etc/machine-id`, the
dbus copy, `etc/resolv.conf`, `etc/hostname`, `etc/ssh/ssh_host_*` and the
hivemind token directory — per-guest identity hygiene, every item of it. The
blast radius is one owner: `template_tags` is keyed `(owner, tag)` and
`ctlops.ownedSnapshot` masks every other owner's snapshot behind the same
not-found a stranger gets, so the only person who ever boots a template is the
person who captured it. Nothing there protects the host, and nothing there
protects another tenant.

So the shape of the fix is: stop asking the host to enforce, on an
attacker-authored filesystem, something only the guest's own owner is affected
by. Two of the six are already solved by machinery nobody noticed was there.

## What is already there

`sparkbox-netcfg` (`hack/build-rootfs.sh`) is a oneshot ordered
`DefaultDependencies=no`, `Before=ssh.service sshd.service`. It reads the
**kernel command line** — which the host writes per boot and no guest can forge
— and already:

- sets the hostname from `sparkbox_host=<name>`, so a fork is named correctly
  from its first boot without anything on its disk being touched at capture;
- rewrites `/etc/resolv.conf` from `sparkbox_dns=`, so a stale resolver in a
  template is overwritten before anything reads it;
- runs `ssh-keygen -A`, which regenerates any host key that is *missing*.

Four of the six deletions are therefore either already handled at first boot or
handled if the file is absent. `sparkbox_host` is the fork marker we were about
to invent: it is host-supplied, per-boot, authenticated by being on the cmdline,
and it already tells a guest what sandbox it is.

## Design

### 1. Fork identity is regenerated by the guest, at first boot

`sparkbox-netcfg` stamps the sandbox name it last configured into
`/var/lib/sparkbox/sandbox`. On every boot it compares the stamp with
`sparkbox_host=` from the cmdline. They match on a resume and on an ordinary
reboot. They differ in exactly two cases: this rootfs is a **fork of a
template**, or the sandbox was **renamed**. Both want the same thing.

On a mismatch, before the existing `ssh-keygen -A`:

- remove `/etc/ssh/ssh_host_*`, so the regeneration that already runs two lines
  later produces a fresh pair instead of reusing the parent's;
- clear `/etc/machine-id` and `/var/lib/dbus/machine-id`;
- write the new stamp.

This runs before sshd, so no service has published the old identity. It costs
one `stat` on a boot that matches.

It is *the guest's own* copy of the sanitizer, and that is the point: the only
party harmed by a template whose owner deleted this hook is that same owner.

### 2. machine-id comes from the cmdline, not from the disk

The one item first-boot regeneration handles badly is `/etc/machine-id`: PID 1
reads it before any unit runs, so a fork rewriting it in `sparkbox-netcfg` is
correct from its *second* boot onward. systemd has an answer already —
`systemd.machine_id=<32 hex>` on the kernel command line, honoured by PID 1
itself.

The driver already builds a per-boot cmdline carrying `sparkbox_host`. It gains
a machine id derived deterministically from the sandbox name, so a fork differs
from its parent with no guest cooperation, no lag, and nothing to trust.

The guest-side clear in (1) stays as the fallback, because it also covers the
dbus copy and the systemd-less slim images.

### 3. Capture stops sanitizing where it cannot, and keeps doing it where it can

`Driver.Snapshot` drops the `DisableHostRootfsMounts` refusal and makes
`sanitizeTemplate` conditional on the same flag. Where the mount is available
(the DGX, a standalone host) it still runs, because a template that is clean at
rest is worth having and this is defence in depth. Where it is not, capture is
reflink + `e2fsck` + `zerofree` + rename — every step of which the cluster
already runs today for checkpoints.

`installAuthorizedKey` keeps its guard unchanged. That one is a real mount of a
real guest disk on the create path and it stays off.

### 4. The strip is done by the gateway, and it fails the capture

This is the actual blocker, and it is not the mount.

Before any rootfs is packed, `Manager.stripEnvForPack` rewrites the managed
`/etc/environment` block to empty so plaintext secret values never ride into a
template or an archive. It reaches the rewriter by type-asserting `m.envSync` —
and **a node never calls `SetEnvSync`**. That is correct on its own terms (an
owner's decrypted secrets must not sit on every machine that runs one of their
sandboxes; the KEK is derived from a key only the gateway holds), but it means
the assertion fails, `stripEnvForPack` returns `nil`, and the pack proceeds with
an uncleared disk.

On CKS the gateway is control-plane-only and every VM lives on the node, so
**every capture is a remote capture**. This is not an edge case there; it is the
only case. Today it is inert because capture is refused. Turning capture on
without this is the whole point of the exercise inverted.

The fix has the shape of the pre-capture agent-tool refresh in `Fleet.Snapshot`:
a gateway-side step over the same guest exec channel, run before the node is
asked to capture. Three differences from that one, all forced:

- **It fails the operation.** A failed tool refresh means a slightly stale
  template; a failed strip means credentials in a disk every fork copies. The
  local path already fails the caller rather than packing an uncleared disk, and
  the remote path must match it.
- **It may wake a paused guest**, because archiving a paused sandbox is the
  common case and a sleeping box cannot be stripped. It wakes it through the
  node directly rather than through `Fleet.EnsureRunning`, which would fire the
  gateway's own env push and race the strip it is about to do — the same reason
  the local path has `resumeOrRecreate`.
- **It holds the box against lifecycle pushes until the pack is done.** The
  existing `quiesced` flag stops *change-time* pushes only; `PushEnv` clears it
  on purpose. A node emits `sandbox.changed` when the wake lands, the gateway's
  `ApplyChanged` turns that into a push, and that push would refill
  `/etc/environment` between the strip and the capture. A fleet-level "this box
  is being packed" gate on `Fleet.pushEnv` and `Fleet.AwaitEnv` closes it.

`Fleet.Archive` needs all of this exactly as much as `Fleet.Snapshot` does, and
gets it in the same place.

### 5. Captures are written to a directory of their own

Found on the cluster, on the first real `snapshot create`, after §1–§4 were
already deployed:

```
cp: cannot create regular file
'/var/lib/sparkbox/images/.snap-vanpelt-test1.ext4.tmp': Read-only file system
```

The strip and the pause had both worked; the driver got as far as the reflink.
`/var/lib/sparkbox` is mounted **read-only** into the VM controller, with
writable `subPath` carve-outs for `control`, `hot/controller` and
`node-identity` — and `images` deliberately not among them. The operator's base
images are laid down by `prepare-vm-assets`, which runs as root with
`SYS_ADMIN` and exits before any guest starts; the controller then only reads
them. That is what stops a compromised controller substituting the rootfs every
future sandbox is created from, and it is worth strictly more than the
convenience of writing captures next to base images.

So captures get `TemplateDir`, a writable directory holding only user-derived
disks, with its own `subPath` mount and its own `chown` to the controller uid.
It is on the same hostPath volume, so `cp --reflink=always` between a VM's disk
and a capture of it still works. Empty means "the same place as `ImageDir`",
which is every single-machine host and is exactly how this behaved before.

Resolution looks in `ImageDir` **first** and only then in the capture dir. That
ordering is the security half: resolving the writable directory first would let
anything able to write a file there shadow `universal`, which is the precise
substitution the read-only mount exists to prevent. Names cannot collide in
practice — a capture is always `snap-<owner>-<name>` — so the ordering costs
nothing and closes the case where that stops being true. `RemoveTemplate`
likewise deletes only from the capture dir: its one caller is `snapshot rm`, and
an operator base image is not the control plane's to delete.

The lesson generalises past this change: **a hardened node's filesystem is
read-only by default and every new thing the controller writes needs its own
carve-out**, chosen deliberately rather than inherited from a directory that
already existed.

## Order of work

1. The gateway-side strip and the packing gate (§4). Needed for archive on any
   fleet, independent of snapshots.
2. Guest-side fork identity regeneration and the cmdline machine id (§1, §2).
3. Drop the refusal (§3).
4. A writable capture directory (§5).
5. Prove it on the cluster.

1 and 2 are the work. 3 is a conditional and a deletion. 4 was not foreseen and
came out of running 1–3 on the cluster.

## Deliberately deferred

Neither of these blocks correctness, and both become real the moment people use
this. Recorded here so that turning capture on is not mistaken for finishing it.

**Templates are unmetered.** `admitCost` counts running sandboxes; a template is
neither running nor charged. On a node with a 25 GiB per-VM ceiling and a pooled
per-owner budget, every template is up to 25 GiB of the hot tier that nobody is
billed for and no admission decision can see. Tag templates make templates
routine rather than occasional, so this stops being theoretical quickly. The
pooled sum already knows how to subtract a template baseline (that landed with
tag templates); what is missing is counting the template itself against its
owner.

**Nothing collects templates.** There is `snapshot rm`, and it is entirely
manual. There is no age-out, no unbound-template sweep, no cap on how many an
owner may hold, and no accounting when a Node is replaced.

**Templates live on an ephemeral tier.** The node-local XFS hot path is what
CoreWeave reclaims with the Node. A user's `cuda` template does not survive Node
replacement, and `snapshot create` says nothing about that. Either the copy
should say so or templates should be checkpointed to the durable object store
like sandboxes can be — a decision, not an oversight.
