Sparkbox

A Sparkbox is a persistent Firecracker microVM built for development and agentic work.

What persists

Your VM disk persists across disconnects, pauses, and cold starts. Treat it like a small server: keep projects in your home directory and commit important work to source control.

Shared resources

CPU and memory are drawn from your owner pool rather than reserved independently for every VM. Idle guest memory can be ballooned down and returned when the VM becomes active. Turbo temporarily increases a VM's working allocation, subject to the owner's burst ceiling and node availability.

Resource sharing changes performance, not disk persistence. Memory pressure does not delete or recreate your VM.

Pinning a VM

Run sparkbox pin inside a VM before starting a server, daemon, or long-running job that must remain continuously available. A pinned VM is not idle-paused and is protected from memory-pressure reclamation. Run sparkbox unpin when the work finishes; sparkbox status reports the current state.

Pinning consumes shared pool capacity continuously. Use it for active background work, not as a default for every VM.

Pausing a VM

Run sparkbox pause inside a VM to stop it now instead of waiting for the idle reaper. Memory and processes are snapshotted, so reconnecting picks up exactly where you left off. The gateway confirms before it pauses, so the line you see is the host’s own rather than a guess.

A pinned VM comes back up on its own at the next host restart. Run sparkbox unpin first if you want it to stay down.

Saving a VM as its tag’s template

A tag already selects a VM’s secrets, its checked-out repositories and its egress. It can also select the disk it boots from. sparkbox snapshot <tag> captures this VM’s disk and points that tag at it, so the next VM you create on that tag starts with everything you installed here.

It is bound to a tag the VM already carries, so the image and the secrets it was built with stay together. It prints what it is about to re-point — and every VM of yours carrying that tag — then asks; --yes skips the question, and with no terminal to ask at it refuses rather than proceeding. Re-pointing never re-bases a VM that already exists: running or paused, each keeps the disk it was created from, and only VMs created afterwards boot from the new template. The previous template is kept.

The capture pauses the VM and ends the session, because it reads the block device and only a paused VM has finished writing to it. Nothing is lost — reconnecting resumes the VM with its processes intact — but the outcome lands minutes later with nobody inside to tell, so read it with ssh ctl@<domain> snapshot ls. default cannot carry a template: every VM you create carries that tag.

HTTPS proxy

Applications listening in a VM can be reached through Sparkbox's authenticated wildcard HTTPS edge. The explicitly exposed development ports are {{COMMON_HTTPS_PORTS}}. Use sparkbox set-port PORT to change the default forwarded port, and sparkbox make-public or sparkbox make-private to change access. See the proxy guide.

Running a dev server

A dev server's own Host-header check and hot-reload client need explicit wiring for a domain that is never localhost. See running a dev server behind the proxy for the per-framework fixes and the .sparkbox/setup.sh convention for replaying the setup on a fresh VM.

Attached repositories

Repositories attached to one of your tags are cloned into this VM at boot, over a short-lived GitHub App token that git fetches on demand — there is no personal access token in the VM. Run sparkbox repos to see what is attached and where it landed, and sparkbox repos sync to clone what is missing. For a write attachment, sparkbox repo authorize OWNER/NAME makes GitHub operations and PRs appear as the VM's owner; repositories not individually authorized continue using the Sparkbox bot token.

A clone that already exists is never touched. Syncing adds; it does not update, reset or delete.

That same credential backs gh, and it reaches further than code and pull requests: gh api repos/{owner}/{repo}/dependabot/alerts, gh api repos/{owner}/{repo}/code-scanning/alerts, gh run list, gh run view <id> --log and gh pr checks all work inside a checkout with no setup. There is no gh dependabot subcommand — security alerts are reachable through gh api only.

Those reads stay read-only whatever the attachment says. A write attachment raises code, pull requests and issues to write; nothing in the VM can dismiss an alert, cancel a run or create a deployment. A 403 on one of them usually means the App was never granted that permission on the repository, which the repos panel in the web console reports per row.

Who this VM belongs to

sparkbox whoami reports the GitHub login and account number of this VM's owner, plus the owner's Sparkbox handle and the VM's name, as key: value lines; --json prints the host's identity document instead.

Before per-repository authorization, gh api user cannot answer because the fallback credential is an App installation token with no user behind it. After sparkbox repo authorize OWNER/NAME, commands scoped to that repository use the linked user's token and GitHub attributes them to that user. An owner with no linked GitHub account has no login to report, and a Sparkbox handle is not a substitute — whoami says so and exits non-zero rather than answering with one.

Commit authorship

git's author is configured at boot from the GitHub account linked to the VM owner, as <id>+<login>@users.noreply.github.com — the address github.com links back to that account without publishing a real one. Commits made in a VM are attributed on push with nothing to set up.

It is written in system scope, so git config --global user.email still overrides it and is never overwritten. An owner with no linked GitHub account gets no author, and git asks for one on the first commit.

Agent harnesses

New VMs include current versions of Claude Code, Codex, Pi, and Hivemind. Sparkbox environment guidance is installed at ~/.agents/AGENTS.md and linked into each harness's global instruction location. Repository-level instructions still apply normally.

This page's own URL is one an agent inside the VM cannot always reach: docs.<domain> is a public DNS name that can resolve to this fleet's own edge, which a VM's own network routing has no path back to. sparkbox docs [docs|proxy|dev-environment] reads the identical content from inside the VM over the always-open metadata channel instead.

Updating the agent tools

The agent CLIs in a VM — claude, codex, pi, hivemind and agent-browser — come from the template the VM was created from, and their own auto-updaters are turned off so one template means one set of versions. Run sparkbox update-tools --check to see each tool against what the host has cached, and sparkbox update-tools to install the difference; every artifact is checked against the host's digest before it replaces anything.

It pulls from the VM's own host, not the internet, so it works on a VM whose egress is filtered by its tag. Each update writes into that VM's own disk and counts against the owner's pool, so run it when something is behind rather than on a timer.

Supported surface

Only documented commands and URLs are public interfaces. Local metadata endpoints, gateway ports, node services, and files outside your home directory may change as Sparkbox evolves.

Sparkbox documentation is served by the gateway version currently running this environment.
